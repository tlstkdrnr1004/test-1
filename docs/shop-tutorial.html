2MySQL 데이터베이스와 폴더 준비 shop DB 와 상품 사진 폴더

무엇을 확인하나요? 프로젝트는 shop 이라는 DB 가 있어야 테이블을 만들 수 있습니다. 테이블은 실행할 때 JPA 가 자동으로 만듭니다 (ddl-auto). 그래서 우리는 DB 한 개만 직접 만들면 됩니다.
  1. Docker 를 썼다면 이미 shop DB 가 있습니다. 설치판을 썼다면 MySQL Workbench 나 명령 프롬프트에서 아래 SQL 을 실행합니다.

6GitHub 저장소와 팀원 초대 저장소 만들기 · 협업자 추가 · main 보호

팀장
왜 main 을 보호하나요? 팀원 4명이 모두 main 에 바로 올리면 서로의 코드를 확인할 수 없고, 깨진 코드가 섞입니다. 그래서 main 에는 Pull Request(PR) 로만 들어오게 하고, 자동 테스트(GitHub Actions)가 통과해야 머지할 수 있게 합니다.

6-1. 저장소 만들기 (github.com)

  1. GitHub 에 로그인하고 오른쪽 위 + → New repository 를 누릅니다.
  2. Repository name 에 shop-team 같은 이름을 입력하고, Public 또는 Private 를 고릅니다 (Private 이면 팀원 초대가 필수입니다).
  3. Add a README file 과 .gitignore 는 체크하지 않습니다 (프로젝트에 이미 있습니다). Create repository 를 누릅니다.
  4. 만들어진 주소(예: https://github.com/팀장아이디/shop-team)를 복사해 둡니다.

6-2. 팀원 3명 초대 (Collaborator)

  1. 저장소 상단 탭에서 Settings → 왼쪽의 Collaborators (또는 Access) 를 누릅니다.
  2. Add people 을 누르고 팀원 3명의 GitHub 아이디를 한 명씩 입력합니다.
  3. 권한은 기본값 Write 로 둡니다. 초대받은 팀원은 메일 또는 알림에서 Accept invitation 을 눌러야 합니다.

6-3. main 브랜치 보호 규칙 (PR 없이는 못 올리게)

  1. 저장소 Settings → Rules → Rulesets (화면이 다르면 Settings → Branches → Add branch protection rule) 를 누릅니다.
  2. 대상 브랜치는 main 으로 정합니다.
  3. Require a pull request before merging 을 켜고, 승인 수는 1 로 둡니다.
  4. Require status checks to pass 를 켜고, 검색창에 build-and-test 를 입력해서 고릅니다. 이 이름은 8장의 GitHub Actions 작업 이름입니다. 아직 목록에 안 보이면 8장을 먼저 끝낸 뒤 돌아와서 켜도 됩니다.
  5. Create 또는 Save changes 를 누릅니다.
순서 주의 첫 프로젝트는 7장에서 main 에 먼저 올린 뒤에 보호 규칙을 켜세요. 보호 규칙을 먼저 켜면 첫 푸시가 거절됩니다. 그래서 6-3 은 7장 다음에 해도 됩니다.

7첫 커밋과 푸시 Commit, Commit and Push, Push

팀장
용어 3가지 커밋(Commit) = 내 PC 에 저장 기록 남기기, 푸시(Push) = 기록을 GitHub 로 올리기, 풀(Pull / Update Project) = GitHub 의 새 기록을 내 PC 로 가져오기.

7-0. IntelliJ 에 GitHub 계정 연결하기 (처음 한 번만)

  1. 메뉴 File → Settings(Windows: Ctrl+Alt+S)를 엽니다.
  2. 왼쪽에서 Version Control → GitHub 를 누르고, 오른쪽 위 + → Log In via GitHub 를 누릅니다.
  3. 브라우저가 열리면 GitHub 에 로그인하고 Authorize JetBrains 를 누릅니다. IntelliJ 로 돌아와서 계정 이름이 보이면 성공입니다.
이 연결을 하지 않으면 Push 할 때 로그인 창이 반복되거나 권한 오류가 날 수 있습니다.

7-1. 저장소 연결 (VCS 활성화)

  1. IntelliJ 메뉴 VCS → Enable Version Control Integration… 을 누르고 Git 을 고른 뒤 OK 를 누릅니다.
  2. 하단 Version Control 탭(단축키 Alt+9, Mac ⌘+9)이 생기면 성공입니다.
  3. 처음 한 번은 Git 저장소를 만드는 것입니다. 잘 보이지 않으면 메뉴 VCS → Create Git Repository… 를 쓰고 shop 폴더를 고릅니다.
  4. 원격 저장소를 연결합니다. 메뉴 Git → Manage Remotes… (또는 VCS → Git → Manage Remotes…) → + → Name: origin, URL: 6-1 에서 복사한 주소 → OK.

7-2. 커밋 대상 확인 (.gitignore)

  1. Commit 창(단축키 Ctrl+K, Mac ⌘+K)을 엽니다.
  2. 왼쪽 목록에 build/, .gradle/, .idea/ 가 없어야 합니다. 있으면 .gitignore 가 제대로 적용되지 않은 것이니 파일을 다시 확인하세요.
  3. build.gradle, settings.gradle, gradlew, gradle/wrapper/…, .github/workflows/shop-ci.yml, src/…, item/…, docs/… 가 보이면 정상입니다.

7-3. 커밋하고 푸시하기

  1. 왼쪽 목록에서 맨 위 체크박스를 눌러 모든 파일을 선택합니다.
  2. Commit message 칸에 아래 문장을 씁니다.
Commit message
chore: Maven 에서 Gradle 로 전환 (수강생 팀 프로젝트 첫 커밋)
  1. 오른쪽 아래 화살표 옆 메뉴(▼)를 누르고 Commit and Push… (단축키 Ctrl+Alt+K) 를 고릅니다.
  2. 푸시 창에서 대상이 origin/main 인지 확인하고 Push 를 누릅니다.
  3. GitHub 저장소 화면을 새로고침합니다. 파일 목록과 커밋 메시지가 보이면 성공입니다.
Push rejected 가 뜨면 원격에 내 PC 에 없는 기록이 있다는 뜻입니다. 메뉴 Git → Pull… 또는 Ctrl+T (Update Project) 로 먼저 가져온 뒤 다시 Push 합니다. 강제 푸시(Force Push)는 팀 프로젝트에서 절대 하지 않습니다.

10충돌(Conflict) 해결 같은 줄을 두 명이 고쳤을 때

충돌이란? 두 사람이 같은 파일의 같은 줄을 서로 다르게 고쳤을 때 Git 이 "어느 쪽을 쓸까요?" 하고 묻는 상태입니다. 다른 줄을 고쳤다면 충돌 없이 자동으로 합쳐집니다. 이 장에서 직접 만들고 해결합니다.

10-1. 충돌 상태 확인

  1. 팀원 B 의 PR(feature/footer-team)이 먼저 머지되었다고 가정합니다. main 의 footer.html 저작권 줄은 이미 … · 팀 A 로 바뀌어 있습니다.
  2. 팀원 C 의 PR(feature/footer-year)을 열면 PR 상단에 This branch has conflicts that must be resolved 가 나타납니다. 이것이 충돌 신호입니다.

10-1-b. 쉬운 방법: GitHub 웹에서 충돌 해결 (처음이라면 이 방법)

  1. 팀원 C 의 PR 화면 아래쪽에 This branch has conflicts that must be resolved 가 보이면 Resolve conflicts 버튼을 누릅니다.
  2. 웹 편집기에 <<<<<<<, =======, >>>>>>> 로 표시된 부분이 보입니다. 표시 사이의 두 줄을 하나의 줄로 고칩니다.
  3. 고친 결과 예: 2025 Shopping Mall Example WebSite · 팀 A
  4. 표시 줄(<<<, ===, >>>)을 모두 지우고 Mark as resolved → Commit merge 를 누릅니다.
  5. PR 화면을 새로고침해서 충돌 경고가 사라지고 build-and-test 가 다시 ✔ 가 되면 성공입니다.

10-2. IntelliJ 에서 충돌 해결하기 (팀원 C)

  4. 충돌이 나면 Merge Conflicts 창이 뜹니다. 파일 footer.html 을 골라 Merge… 를 누릅니다.
  5. 세 칸짜리 병합 창이 열립니다. 왼쪽은 내 변경(2025), 오른쪽은 main 의 변경(팀 A), 가운데는 결과입니다. 가운데 줄에 두 변경을 모두 담은 한 줄을 직접 씁니다.

    13-2. 3-A · GitHub Actions CD (AWS Elastic Beanstalk 배포) — 선택 실습

    2. GitHub 저장소 Settings → Secrets and variables → Actions → New repository secret 에 AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY 두 개를 등록합니다. 값은 화면에 다시 보이지 않습니다.

    3. 책 부록과 같은 구조의 cd.yml 을 씁니다 (아래 예시). JDK 는 25로 맞춘 점, 그리고 chmod 와 빌드 단계가 shop 에 맞게 바뀐 점을 확인하세요.

    .github/workflows/shop-cd.yml (예시 · 심화)
    name: shop CD

on:
  push:
    branches: [ "main" ]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: corretto
          java-version: '25'
          cache: gradle

      - name: 실행 권한 주기
        run: chmod +x ./gradlew

      # 테스트는 shop-ci.yml 이 이미 합니다. 여기서는 jar 를 만들기만 합니다.
      - name: jar 만들기 (테스트 제외)
        run: ./gradlew bootJar -x test

      - name: 배포 파일 이름 만들기

        uses: einaregilsson/beanstalk-deploy@v20
        with:
          aws_access_key: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws_secret_key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}

          environment_name: shop-env
          version_label: github-${{ github.run_number }}
